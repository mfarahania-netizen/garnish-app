# Household v1 expand-compatible migration plan

Status: design only. **No migration file has been created or applied.**
Production operations: forbidden by this program until the implementation gate and a separate human production decision pass.

## Reality check

- **[Confirmed]** The Stage A base is `1631dc5dbf0f0d5b9699399ed8f50ebef4b053ab`; the current schema has no household tables.
- **[Confirmed]** Personal tenancy is embedded in existing `MealPlan`, `ShoppingList`, `PantryItem`, and `Notification` relations (`apps/server/prisma/schema.prisma:361-426`, `:754-767`).
- **[Confirmed]** `MealPlan(userId,weekStart)` and `ShoppingList(userId)` are already unique, but `MealSlot` is not unique by slot and current shopping semantic dedupe is application-only (`apps/server/prisma/schema.prisma:361-414`; `apps/server/src/shopping-list/shopping-list.service.ts`).
- **[Confirmed]** The existing shopping hardening migration added the list-owner unique key without a duplicate remediation script (`apps/server/prisma/migrations/20260628140000_shopping_list_hardening/migration.sql`).
- **[Decision]** Do not mutate current personal resources into household resources in the first migration. Add a parallel household schema, gate writes, and offer an explicit idempotent copy only after H1–H5 integrity tests pass.
- **[Risk]** Current PWA API runtime caching and account-local browser state can leak one account’s data to another. Database expansion does not solve that prerequisite (`apps/web/vite.config.js:34-39`, `apps/web/src/context/AuthContext.jsx:19-22`, `:154-159`). Household activation remains blocked until cache/session isolation passes.

## Migration principles

1. Expand before contract; new tables and nullable columns only in v1 rollout.
2. Previous application build must continue to read/write personal models during the expand window.
3. No blanket household backfill and no automatic merge of personal food data.
4. Every new uniqueness rule gets a preflight query and a concurrent race test.
5. Database constraints are the integrity boundary; service checks improve errors but do not replace constraints.
6. New writes are feature-flagged and start with internal/disposable users.
7. Application rollback disables new writes but retains new tables/data. Database rollback does not drop data.
8. Contract/drop work is a later program after observed legacy traffic is zero, export/retention decisions pass, and a restorable backup is proven.

## Required gates before any local migration rehearsal

- Stage A documents approved, especially domain model, permission matrix, threat model, and privacy matrix.
- Local/dev `DATABASE_URL` positively identified; command aborts for non-local/non-allowlisted host/database.
- Disposable database or sanitized snapshot only; never production.
- Current migration history clean; `prisma migrate status` and schema/client generation pass.
- Current build and relevant tests recorded.
- P0 account/consent/private-cache findings resolved or implementation verdict remains blocked.
- Migration SQL reviewed for `DROP`, destructive `ALTER`, unbounded update, missing index, and unsafe default.

## Phase 0 — inventory and preflight (no writes)

Record row counts and bytes for affected legacy tables, FK/orphan checks, existing migration status, PostgreSQL version/extensions, and query plans. Run at minimum:

```sql
-- Existing plan duplicates (MealPlan is expected clean; MealSlot is not guaranteed).
SELECT "userId", "weekStart", count(*)
FROM "MealPlan" GROUP BY 1,2 HAVING count(*) > 1;

SELECT "mealPlanId", "dayOfWeek", "mealType", count(*)
FROM "MealSlot" GROUP BY 1,2,3 HAVING count(*) > 1;

-- Existing owner/list invariant.
SELECT "userId", count(*)
FROM "ShoppingList" GROUP BY 1 HAVING count(*) > 1;

-- Candidate semantic duplicates only; report, do not auto-delete.
SELECT si."shoppingListId",
       lower(regexp_replace(trim(si."name"), '\\s+', ' ', 'g')) AS candidate_key,
       count(*)
FROM "ShoppingItem" si
WHERE si."isChecked" = false
GROUP BY 1,2 HAVING count(*) > 1;

-- Orphans that would invalidate later relations.
SELECT count(*) FROM "MealSlot" s
LEFT JOIN "MealPlan" p ON p.id=s."mealPlanId" WHERE p.id IS NULL;

SELECT count(*) FROM "ShoppingItem" i
LEFT JOIN "ShoppingList" l ON l.id=i."shoppingListId" WHERE l.id IS NULL;
```

The SQL normalization is only a candidate report; the canonical Persian/ingredient-aware key is generated by a versioned application function. Duplicate resolution requires a report with IDs, provenance, quantities, and checked state. Never sum incompatible units automatically.

### Baseline integrity repair gate

The personal `MealSlot` duplicate risk exists independently of household tables. Before adding `UNIQUE(mealPlanId,dayOfWeek,mealType)`:

1. stop/flag personal slot writes in the rehearsal environment;
2. export duplicates;
3. choose the survivor deterministically (latest meaningful update cannot be inferred because current rows lack `updatedAt`; human/product rule required);
4. update the service from delete-then-create to conflict-safe upsert/CAS;
5. add the unique index;
6. race-test two concurrent creates.

**[Gate-critical]** Do not add the index while duplicates remain, and do not claim the risk fixed by a transaction alone.

## Phase 1 — H1 foundation expansion

Suggested migration: `*_household_h1_expand`.

Create only:

- household/membership/invite/member-profile/data-grant tables;
- idempotency table;
- household activity table plus independent realtime/notification consumer-work and checkpoint tables;
- required enums or text checks;
- foreign keys, unique keys, and queue/replay indexes.

Key constraints/indexes:

- unique membership `(householdId,userId)` for non-null users;
- active membership requires non-null user; ended membership may be pseudonymized after erasure;
- unique invite digest;
- invite target check requires `targetUserId` or versioned HMAC `targetAddressDigest`; store independent target-digest key version, never a plain email/phone hash; raw delivery address is transient/encrypted and excluded from logs/events;
- index invite `(householdId,status,expiresAt)`;
- unique activity `(householdId,sequence)`;
- unique event work `(eventId,consumer)`, claim index `(consumer,status,nextAttemptAt)`, and checkpoint `(householdId,consumer)`; every event inserts both realtime and notification work. Before H3 the active projector marks work `DONE/DISABLED_BEFORE_CUTOVER` with sequence/policy version instead of accumulating backlog; no-policy work is `DONE/NO_POLICY`;
- unique data grant `(profileId,scope)`;
- unique idempotency `(principalId,operation,key)`, `responseExpiresAt`/`tombstoneExpiresAt` indexes, full result retained at least 30 days, compact tombstone through day 90; offline commands expire at seven days;
- check guest membership has `expiresAt`;
- household status check uses `ACTIVE|ARCHIVED|DELETING`; PRD `DELETION_PENDING` maps to `DELETING`, while completed `DELETED` means row/tombstone absence rather than a live tenant state;
- household owner FK uses `RESTRICT` so account deletion must transfer/delete explicitly.

Because tables are new/empty, ordinary index creation is appropriate in disposable rehearsal. If any index is later added to a large populated table, use an approved online/concurrent procedure outside a Prisma transaction as required by the deployment environment.

Deployment order:

1. apply expand migration;
2. deploy server that can read absent/present household state and handles owner restriction in account deletion;
3. keep `HOUSEHOLD_CREATION_ENABLED=false`;
4. run H1 integration/IDOR/invite/owner tests;
5. enable only for internal test accounts.

Rollback: disable creation and household routes. Keep tables. There is no down migration that drops household data.

## Phase 2 — H2 pantry/shopping expansion

Suggested migration: `*_household_h2_shopping_expand`.

Create household pantry, shared list, semantic household item, item-contribution, session, decision/option, and attachment metadata tables. Do not change legacy `ShoppingList`/`ShoppingItem` yet.

Key constraints:

- unique `(householdId,listKey)`;
- unique `(listId,activeSemanticKey)` with terminal rows setting key null;
- unique contribution `(listId,sourceKey)` and index `(itemId,status)` so multiple requesters/meal sources converge without losing provenance;
- unique active session `(listId,activeKey)` with `activeKey='ACTIVE'` or null;
- every child has direct household ID or a composite/validated FK path; queries still include household scope;
- versions default to 1 with checks `version >= 1`;
- decision selected option must belong to the same request (composite FK or transaction + constraint trigger reviewed explicitly);
- attachment metadata has no public path and scan status defaults to `PENDING`.

Write rollout:

1. read-only household list endpoint;
2. controlled creates with idempotency/unique-conflict behavior;
3. status/CAS transitions;
4. sessions/decisions;
5. attachments only after upload security gate.

The item state check permits only `NEEDED→CLAIMED→IN_CART→BOUGHT` or `...→UNAVAILABLE→DECISION_PENDING→SUBSTITUTION_APPROVED` (then replacement purchase) / `SKIP_APPROVED→SKIPPED`, plus explicit undo transitions approved by product. Applying a plan diff mutates only deterministic plan contribution source keys and recomputes aggregates; manual/other-meal contributions are invariant.

Race rehearsal includes semantic item/contribution insert, concurrent plan/manual sources, safe plan-diff removal, session start, quantity edit, bought/unavailable, and decision resolution with at least two database connections.

Rollback: flag household shopping read-only/off. Preserve rows and storage; revoke temporary signed URLs.

## Phase 3 — H3 notification expansion

Suggested migration: `*_household_h3_notification_expand`.

Reuse—not recreate—the H1 event-consumer-work/checkpoint tables. Create `NotificationIntent`, preference, and intent-delivery tables. Alter legacy `Notification` only to add a nullable unique `intentId` link and compatible visible-inbox fields; do not rename/drop old columns or store muted/push-only intents there.

Legacy rows stay visible legacy inbox data. Do not fabricate `NotificationIntent`, source event, dedupe, hidden channel decision, or push delivery for them. `isRead` remains the compatibility source unless a separately reviewed visible-field backfill is exact.

Indexes:

- inbox `(userId,createdAt desc)`;
- unread `(userId,readAt,createdAt)`;
- intent unique `(recipientUserId,sourceEventId,eventType)`;
- delivery claim `(channel,status,nextAttemptAt)` and unique `(intentId,channel)` for both `IN_APP` and `PUSH` decisions;
- nullable unique `Notification.intentId` so only an available in-app decision creates one legacy-compatible visible row;
- preference `userId` unique.

Deploy preference API before UI switches authority. `NotificationIntent` is canonical; new projection writes deterministic `IN_APP` and `PUSH` decisions and creates legacy `Notification` only for `IN_APP=AVAILABLE`, so push-only preferences work without rollback leakage. At H3 activation, transactionally record an audited per-household cutover sequence/policy version from the reused H1 checkpoint; only greater sequences may create intents. Historical work remains completed no-op and is never reinterpreted. Household presentation remains off until cross-device preference, poison-event isolation, cutover/no-backlog, checkpoint, and duplicate-worker tests pass. Push remains off.

Rollback: router/delivery flags off; previous application continues using old notification columns. Keep new preference as authoritative when re-enabled; never silently fall back to stale localStorage for sending.

## Phase 4 — H4 meal board expansion

Suggested migration: `*_household_h4_meal_board_expand`.

Create board, immutable plan-version, household slot, proposal, reaction, attendance, and shopping-diff tables. Do not alter legacy `MealPlan`/`MealSlot` tenancy.

Key constraints:

- unique `(householdId,weekStart)`;
- unique `(boardId,versionNumber)`;
- unique `(planVersionId,localDate,mealType)`;
- board status includes persisted `SUGGESTIONS` between draft and review;
- slot has one integer `guestCount` with check `0 <= guestCount <= 20` and version/CAS; attendance rows contain no guest count;
- unique reaction `(proposalId,profileId)`;
- unique attendance `(slotId,profileId)`;
- unique diff `(fromVersionId,toVersionId,diffHash)`;
- immutable-version enforcement in service plus database privilege/trigger review; no update endpoint for version/slot snapshots;
- board advance uses expected current version in one transaction.

Rehearse concurrent proposal/confirm, duplicate slot, self/managed attendance, two writers racing slot-level guest count, bounds/double-count prevention, serving calculation, stale base, deterministic diff, apply retry, and rollback/read of old immutable versions.

Rollback: prevent new board advances; existing immutable versions remain readable. Never rewrite them into the legacy personal plan automatically.

## Phase 5 — H5 secure share expansion

Suggested migration: `*_household_h5_share_expand`.

Create share, share-version join, share-scope, contextual comment, and advisor-proposal tables.

Key constraints/indexes:

- unique token digest; digest only, never plaintext;
- digest key version for pepper rotation;
- required expiry and status checks;
- unique `(shareId,planVersionId)` and `(shareId,scope)`;
- advisor proposal references an immutable base version selected by the share;
- indexes for expiry/revocation cleanup and open proposals;
- comments/proposals have bounded length and no canonical-plan FK path that cascades into writes.

No sensitive scope backfill exists; absent scope is denied. Test generated token entropy/digest, simultaneous revoke/read, scope reduction, advisor write denial, fragment-to-memory consumption, and immediate `history.replaceState` fragment scrubbing before enabling external routes.

Rollback: revoke/disable all share routes via kill switch; keep rows for bounded audit/restore. Immediately invalidate application/cache projections.

## Phase 6 — optional explicit legacy copy (not blanket backfill)

This phase begins only after H1–H5 hard gates pass. Add a small `HouseholdLegacyImport` ledger with unique `(userId,resourceKind,sourceFingerprint)` and status/result counts. The user explicitly selects a target household and preview.

Copy rules:

- personal list: copy each active row as a `LEGACY_COPY` contribution with deterministic source key/original row ID under a semantic aggregate; conflicts become preview decisions, not auto-merged quantities;
- personal pantry: copy with canonical key; conflicts reported;
- personal meal plans: copy selected current/future weeks into immutable board version 1; duplicate slots block the affected week;
- allergies/health/preferences: never copy into shared profile; create no data grant without explicit subject action;
- notifications/events: do not copy;
- original personal rows remain unchanged.

The operation is one idempotent job per resource group, resumable and reportable. The new UI must clearly distinguish personal vs household data; do not dual-write both models because partial failure creates unresolvable divergence.

Rollback disables new imports. Previously copied household data remains and may be deleted by an explicit household action; original personal data is still present.

## Phase 7 — contract (future program, not v1)

No legacy column/table/endpoint is dropped until all are true:

- at least two compatible releases have run;
- telemetry, sampled logs, and database counts prove zero required legacy reads/writes for an approved observation window;
- every active user has a documented personal/household disposition;
- export, erasure, retention, owner-deletion, and household deletion jobs pass;
- a sanitized restore rehearsal proves the backup;
- founder, security/privacy, and release human gates approve destructive work.

Contract changes must be small and reversible where possible. “Schema cleanup” is not a user outcome and must not be bundled with H1–H5.

## Account deletion and shared ownership migration rule

Before household creation is enabled, the account deletion service must:

1. find owned households;
2. require transfer or household deletion—never orphan ownership;
3. mark non-owner memberships ended and remove access;
4. revoke personal data grants and device/push bindings;
5. pseudonymize membership/profile/activity attribution according to approved retention while preserving household-owned content;
6. delete user-owned private data.

Active membership requires a live user ID; ended membership may set it null after attribution is pseudonymized. This behavior must be rehearsed with owner, adult, member, managed profile, and sole-member household.

## Rehearsal matrix

Run every migration on:

1. empty disposable database;
2. current local dev schema with representative data;
3. sanitized snapshot containing maximum known row counts and constructed duplicates/orphans;
4. previous application build against expanded schema;
5. new application build with feature flags off and then on;
6. interrupted backfill/import resume;
7. application rollback with new rows present.

Evidence to capture:

- exact database fingerprint proving non-production;
- migration names/checksums/status and wall/lock time;
- row counts before/after per table;
- duplicate/orphan preflight output;
- query plans for tenant, event replay, outbox, inbox, and delivery indexes;
- build/test commands/results;
- rollback flag behavior and data preservation;
- no unexpected `DROP`, delete count, or table rewrite.

## Test gates

- permission matrix and IDOR suite;
- invite/share single-use, expiry, revoke, hash-at-rest;
- invite target-binding CHECK, no-target mint rejection, versioned target HMAC rotation/match, and raw-address log/event absence;
- owner transfer/last-owner/account deletion;
- member removal racing an ordinary mutation in both lock orderings; no mutation after removal commit;
- semantic item/active session/meal slot uniqueness under concurrency;
- multi-source shopping contribution/provenance and plan-diff preservation of manual/other-meal contributions;
- idempotency and outbox crash windows;
- seven-day offline expiry versus 30-day full idempotency result/90-day tombstone behavior;
- independent realtime/notification consumer progress, poison projection, duplicate worker/preference/quiet enforcement;
- H1/H2 notification-disabled no-op checkpoint and H3 audited cutover with zero historical notification flood;
- two-browser realtime and offline reconnect;
- PWA/account A→B cache isolation;
- household deletion and storage cleanup;
- Prisma client generation and current/new application builds.
