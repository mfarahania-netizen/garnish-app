# PERSONALIZATION & RECOMMENDATION — FORENSIC AUDIT (حسابرسی بدون تعارف)

**Scope:** the full personalization & recommendation system — profile → signals → loop → ranker → what the user sees.
**Method:** synthesis of 5 adversarial audits (algorithm, integrity, mind-reading, data, architecture), one system map, and 4 world-research briefs (recsys SOTA, TikTok/IG/Spotify, cooking-apps, mind-reading UX). Every claim is grounded in `file:line` confirmed by the underlying auditors.
**Stance:** evidence-only, no flattery. The founder grades to a billion-dollar bar and asked the unvarnished truth.

---

## 1. حکم نهایی — Executive Verdict

The founder's instinct is right, and the four independent auditors converge on it from four different angles. Garnish has built a **genuinely good content/safety substrate and an honestly-engineered staging lane — and then wired almost none of the intelligence to a real user.** The system that actually ships on `GET /recommendations` is a **fixed-weight linear blend of keyword-token heuristics** (`ranking.service.ts:96-107`, weights the code itself admits were "carved by hand to sum to 1.00" at `:91-95`), fed by a **profile hardwired to empty behavioral observations** (`profile-read.service.ts:112`), receiving **zero runtime context** (`recommendation.controller.ts:36-39`), where the single highest-intent action — **cooking a recipe — is a silent no-op** because `cook_complete` has no processor and is dropped by the event router (`processor.registry.ts:22-49`, `event-router.service.ts:10-13`). Every sophisticated thing the founder was promised — learned embeddings, collaborative filtering, a self-improving loop, context, the nDCG "learning proof" — exists only as **default-OFF shadow code whose output is explicitly discarded** (`recommendation-pipeline.service.ts:76-79`) and whose own activation gate is hardcoded to `promotionAllowed: false` (`recommendation-founder-review-evidence-pack.ts:21`). It is not a recsys with a staging lane; it is a staging lane with no recsys attached. The one "proof of learning" is a **circular synthetic simulation** where the same module writes both the behavior and the relevance metric (`recommendation-learning-proof.ts:76-124`).

**Headline: ~12% of the way to the world-class "mind-reading" system the founder wants.** The founder's "<10%" claim is **essentially correct, and generous in one direction, harsh in another.** It is generous because the *plumbing* is real and well above category norm: a true HARD allergy gate, candidate-source diversity, exposure de-dup, USDA-locked nutrition, and ingredient-level content data that is a genuine moat (the research is unanimous that this is exactly the asset that lets a learning engine work at low scale). It is harsh only in that the felt experience could be lifted dramatically with cheap arithmetic, not GPUs. But on the dimension the founder actually means — *does it learn me, does it read my mind, does the loop close* — the honest per-dimension scores are: **algorithm ~10–15%, integrity ~35%, mind-reading ~8–12%, data/scale ~25%, architecture ~20%.** Blended against the vision (not against competitors), **~12%.** The founder is not being too hard on it. The gap between the marketing-grade shadow code and the dumb path that ships is the whole story.

## 2. آنچه واقعاً کار می‌کند — What Genuinely Works (no flattery, only real strengths)

- **The HARD allergy gate is real and inviolable.** Three-layer safety (reconciliation precedence=`declared_safety`, signal-calculator correction guard, AI grounded-reply check) — declared allergens are never overwritten by behavior (`profile.md:83-88`, `signal-calculator.service.ts:181-209`). This is the strongest version of "integrity before ranking" in the whole recipe category and a genuine trust moat.
- **The read side is real and serves users.** `GET /recommendations` is genuinely what Home and Discover render; it rebuilds the feature vector live from raw events on every pipeline call and a 10-component ranker consumes it (`recommendation-pipeline.service.ts:32`, `ranking.service.ts:137`). The *shape* (candidate gen → rank → re-rank) is correct — it is a two-stage funnel in embryo.
- **Candidate-source diversity exists.** An 8-bucket generator (`similar`, `embedding`, `trending`, `health`, `seasonal`, `inventory`, `cold_start`, `collaborative`) gives real recall variety (`candidate-generator.ts`).
- **The negative-feedback loop is correctly wired.** Dismiss → `applyNegativeFeedback` actually closes (`useDismissRecommendation.js:21` → `recommendation.signal-processor.ts:45-46`). It is the one live taste-learning path.
- **Honest cold-start, honest 501 stubs.** No fabricated taste; declared prior capped at 0.20; dead admin routes throw `NotImplementedException` rather than pretending (`recommendation.controller.ts:114-211`). The code does not lie about itself internally — the dishonesty is between the shadow tree's grand names and its dead wiring, not in the live stubs.
- **The content moat is real.** Ingredient-level feature data + GRIS + USDA-locked nutrition is exactly the asset every research brief says enables a *learning* engine from interaction #1 without collaborative data. The raw material for world-class is present; it is simply not connected.

## 4. پنج مشکل سیستمیِ بزرگ — The 5 Biggest Systemic Problems

1. **The loop is severed at the most important joint: cooking teaches nothing.** (C1+C2+C3) The marquee action drops on the floor (`cook_complete` unrouted), the live profile is hardwired to empty observations (`profile-read.service.ts:112`), and the positive taste extractor only fires on events the web never emits. The result: the founder's own acceptance test ("cook 10 stews → more stews tomorrow") is *false*, and no amount of ranker tuning fixes it because the ranker is fed declared prefs + two hardcoded Persian-name signals, not behavior. **Until the cook loop closes and the profile hydrates from real observations, there is no personalization to speak of — only declared filtering with a heuristic re-sort.**

2. **All the intelligence is in a shadow tree that is architecturally forbidden from shipping.** (C5+C8+H8) Cuisine affinity, the collective co-occurrence prior, the learning proof, ~13k LOC of runtime-shadow + activation labs — every one is `productUseEnabled:false`, output-discarded, and gated by a verdict hardcoded to "no" (`recommendation-founder-review-evidence-pack.ts:21`). This is the inverted-effort core finding: the most sophisticated, best-tested 10 files influence nothing a user sees, while the product runs on ~1,500 LOC of heuristics. It is *worse than absent* because it masks the thinness and is a permanent maintenance tax on a solo founder.

3. **It is not a learning engine — it is hand-tuned heuristics with a fake proof.** (C4+C7+H4) The founder explicitly demanded "a self-improving learning engine, not 100 lines of filter code." What ships is exactly that: fixed weights carved to sum to 1.00, keyword token-matching standing in for taste modeling, no learned model, no user embedding, and a "proof of learning" that is a circular synthetic simulation grading its own homework. There is zero validation on a single real user. The strategic unlock the research identifies — *content-grounded learned embeddings personalize from interaction #1* — is exactly the moat Garnish has and isn't using.

4. **It is context-blind and pull-only — there is no "mind-reading" surface at all.** (C6+C9+H6+H7) The live path takes only `userId`+`limit`; recs are identical at 8am and 11pm. The contextual surfaces the user *sees* are theater (pantry rail = a rec-list slice, AI Whisper = hardcoded "for tonight"), the one genuinely time-aware component (Daily Briefing) is unwired, proactivity is default-OFF with no push channel, and explanations are debug-panel percentages instead of "because you cooked X." The UX research is unanimous that context + legibility + restraint is *most* of the felt magic — and it is the cheapest tier of work (copy, rules, timing over data already owned) — yet none of it reaches the user.

5. **No collective intelligence and no network effect — every user is a population of one, structurally and cold forever.** (C8+H1+H2+H3+H5) No CF in production, no cohort/region prior, no popularity *deflation*, no exploration bandit, cuisine invisible to the taste layer, and warm-up thresholds real users never hit. The founder's three concrete examples — 1M users each different, 200 dishes everyone skips, a fish-leaning region — have **no live mechanism for any of them.** The research shows all three are achievable with *arithmetic* (Beta-shrunk accept-rate, hierarchical shrinkage, Thompson sampling) over data already logged — but none of it is wired.

The positive loop — cook, favorite → taste — is severed: `cook_complete` is dropped (C1), the live profile ignores all observations (C2), and the positive extractor is dead code (C3). **Cook 10 stews → tomorrow is unchanged.** | C1, C2, C3, M4 |

## 6. The single highest-leverage sequence (from the research, grounded in our code)

This is not new scope — it is *connecting what exists*. In ROI order: **(0)** materialize per-recipe + per-cohort event counters (the substrate everything needs); **(1)** close the cook loop (C1) + hydrate the live profile (C2) + route favorites through `extractSignalsFromRecipe` (C3); **(2)** popularity deflation — Beta/Wilson cohort-conditioned accept-rate (H2, founder ex.#1); **(3)** cohort/region prior via hierarchical shrinkage (H1+H5, founder ex.#2); **(4)** Thompson explore slot (H3 — the flywheel); **(5)** item-item co-engagement CF (C8); **(6)** plumb time-of-day context + "because you cooked X" recsplanations (C6+H6 — the cheapest "it gets me" win). Defer: two-tower, ANN, user embeddings, Monolith — all scale stories with no rewrite cost later. Throughout: replace the circular nDCG proof with a temporal held-out eval + interleaving (C7), and delete/extract the shadow tree (C5/H8) to free the maintenance budget.
