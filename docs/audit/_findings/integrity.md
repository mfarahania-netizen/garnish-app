# FORENSIC AUDIT — End-to-End Integrity (does the loop actually close?)

**Dimension:** End-to-end personalization loop — user does X → signal → profile → ranking → what the user sees next.
**Reviewer stance:** skeptical, evidence-first, no flattery. Every claim cites `file:line` confirmed from source (not from the map).

## Blunt verdict

The loop is **partially wired and partially fake**. The *read* side is real and impressive: `GET /recommendations` is genuinely what Home and Discover render, it rebuilds the feature vector live from raw events on every call, and a 10-component ranker consumes it (`recommendation-pipeline.service.ts:32`, `useHomeData.js:29`, `useDiscovery.js:104`, `ranking.service.ts:137`). But the *write* side is broken in three load-bearing places, and the single most important user action — **cooking a recipe — is a no-op for personalization**. The web app emits `cook_complete` (`useCook.js:101`), but there is **no processor registered for `cook_complete`** (`processor.registry.ts:22-49`) and the event router silently drops any unmatched type (`event-router.service.ts:10-13`); `cook_complete` is also absent from every feature-store event window (`feature-store.service.ts:184,230-239`). Worse, the entire positive-taste signal extractor (`extractSignalsFromRecipe` → `likes_stew`, `likes_chicken`, …) only runs on `recommendation_cook`/`recommendation_save` (`signal-calculator.service.ts:60-67,129`), and **those events are never emitted by the web app** — they exist only as unused taxonomy constants (`eventTaxonomy.js:128-130`, zero `trackEvent` call sites). So viewing or favoriting 10 Persian stews writes only `likes_high_protein`/`prefers_vegetarian` (`recipe.signal-processor.ts:20-53`) — never `likes_stew` — and cuisine ("Persian") has no signal anywhere. The honest answer to the harshest question: **if I cook 10 Persian stews, the app verifiably does NOT surface more like them tomorrow.** The only live taste-learning path is *negative* (dismiss → `applyNegativeFeedback`, which is correctly wired: `useDismissRecommendation.js:21` → `recommendation.signal-processor.ts:45-46`) plus a weak content-recall path (`recipe_view`/`favorite_add` → candidate "similar" bucket via shared search-terms: `candidate-generator.ts:82-112`). **How close to the vision: ~35%.** The architecture and ranker are 80%-grade; the closed loop that proves "behavior changes recommendations" is ~35% because the marquee action (cook) and the entire positive taste-extraction path are dead in production.

## The 3 things that would most move this dimension toward world-class

1. **Close the cook loop for real.** Register a `cook_complete` processor that runs the full positive-feedback extraction (`extractSignalsFromRecipe` + `applyIngredientSignals` + `SignalObservation`), and add `cook_complete` to the feature-store engagement windows and candidate-generator seed sets. This single change is what makes the founder's "cook 10 stews → more stews tomorrow" claim actually true. Today it is false.

2. **Make real engagement (favorite/view) build the full taste vector, and add cuisine affinity.** Re-point `favorite_add` (and the new cook processor) through `extractSignalsFromRecipe` so saves/cooks write `likes_stew`/`likes_chicken`/per-ingredient signals — not just `likes_high_protein`. Add the already-designed `cuisine_affinity` signal so "Persian" is learnable and rankable. Delete or wire the dead `recommendation_save`/`recommendation_cook` taxonomy constants so the codebase stops implying a path that has no producer.

3. **Guarantee freshness and durability of the write→read handoff.** Make `rank()` responsible for (or assert) a fresh feature vector, and process high-value feedback events through a durable outbox with await/retry instead of fire-and-forget, so a dismiss/cook reliably influences the very next fetch. Then add a single end-to-end integration test that proves it: cook N stews → assert stew-similar recipes rank higher on the next `GET /recommendations`. No such test exists today (the learning proofs in `recommendation-learning-proof.ts` are synthetic simulations, not the live ingest→rank path).

---

### 4-line summary
- **dimension:** End-to-end integrity (does the personalization loop close?)
- **verdict:** Read side is real and serves users; write side is broken — the cook action and the entire positive taste-extraction path are dead in production; only the negative (dismiss) loop and weak view/favorite content-recall actually close. ~35% to vision.
- **#critical:** 3
- **single biggest problem:** Cooking a recipe is a personalization no-op — `cook_complete` has no processor and is dropped by the event router, and the positive-taste extractor only fires on `recommendation_cook`/`recommendation_save` events the web app never emits, so "cook 10 Persian stews → more like them tomorrow" is verifiably false.
