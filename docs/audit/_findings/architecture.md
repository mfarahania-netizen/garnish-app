# FORENSIC FINDINGS — Architecture & Shippability (value vs over-engineering)

**Dimension:** Is the recommendation subsystem real, shippable value, or elaborate scaffolding that never reaches a user? Coupling, complexity, maintainability for a solo non-technical founder, and the ratio of code-that-serves-users to code-that-only-serves-itself.
**Reviewer stance:** skeptical Principal/Staff, evidence-only, no flattery («بدون تعارف»).

## Blunt verdict

The recommendation directory is **~90% gold-plating**. Of 108 non-test source files (and 207 total `.ts` including 99 spec files), the code that actually serves a user request is roughly **nine files** — `pipeline/{recommendation-pipeline.service, candidate-generator, ranking.service}`, `taste-affinity/taste-affinity.builder`, `exposure/exposure-tracking.service`, `explainability/explainability.service`, `ranking-model/contribution-calculator` — reached by exactly **two live web calls**: `GET /recommendations` and `POST /recommendations/impression` (`apps/web/.../useDiscovery.js:106`, `useHomeData.js:29`, `useFavorites.js:31`, `useImpressionObserver.js:31`). Everything else is a cathedral built for itself: the `runtime-shadow/` tree is **79 source files / ~9,092 LOC + 4,196 LOC of tests**, every one of which is default-OFF, admin-gated to 403, its output explicitly discarded (`recommendation-pipeline.service.ts:78`), and whose own "founder review / activation" sub-system hardcodes `promotionAllowed: false` (`recommendation-founder-review-evidence-pack.ts:21`) — i.e. thousands of lines whose sole job is to evaluate whether to ship the shadow engine, permanently answering "no." This is not a recsys with a staging lane; it is a staging lane with no recsys attached to it. For a **solo non-technical founder** this is the worst possible outcome: a large, intricate, internally-consistent, well-tested body of code that a maintainer must understand and carry, yet that moves zero product metrics and cannot be safely deleted without reading 13k lines to confirm nothing live depends on it (it doesn't). The genuine live value (candidate diversity, an allergy gate, exposure de-dup, a heuristic ranker) could live in ~1,500 LOC. Honest distance to a world-class, shippable architecture: **~20%** — the live skeleton is sound and isolated, but the sophistication is almost entirely *unearned* because it never reaches a user, and the maintenance liability it creates for a non-technical owner is severe.

## The 3 things that would most move this dimension toward world-class

1. **Delete or extract the entire `runtime-shadow/` tree (~13k LOC incl. tests).** It serves no user, its output is discarded by design, and its activation verdict is hardcoded to "no." Either promote *one* signal (cuisine affinity or the collective prior) into the live ranker behind a flag with real online metrics, or remove the whole branch. This single act roughly halves the slice's footprint and removes the biggest maintenance liability for a solo non-technical founder — with zero user-facing regression (verified: the web app references none of it).
2. **Collapse the architecture to "one live pipeline + one optional flagged challenger."** Real recsys infra is: candidate gen → rank → log → (optional) shadow/challenger ranker measured against the live one on *online* metrics. That is ~1 module, ~6 providers, 1 controller. The current 7-controller / 25-provider module with control-plane/lab/founder/activation sub-systems is enterprise process-theater that a billion-dollar product would add *after* product-market fit, not before a single user is personalized.
3. **Reinvest the freed effort into the ~9 files that actually ship.** Break up the 1,200-LOC `ranking.service.ts`, and put the 4,196 lines of "prove OFF stays OFF" test energy onto the live ranker, candidate generator, and the allergy gate — the code paths a real user actually hits. Earn the sophistication on the live path before building governance for a path that isn't live.
